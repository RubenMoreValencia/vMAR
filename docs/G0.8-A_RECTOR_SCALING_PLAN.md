## Objective

Identify no more than one high-value mathematical capability per iteration
from the DSNeuralRNAS ecosystem and promote it only where it adds a distinct,
testable contribution to the system-dynamics learning philosophy.

The normative mapping is `G0.8-A_SCALING_MATRIX.csv`:

`original function → mathematical principle → contract → equivalence
→ improvement → vMAR module → acceptance test → decision`.

## Priority and admission rule

1. **P0 — frozen baseline:** M0/M1 stable, M2/M3 optional, dual R/C23
   parity, strict 14/14 historical fixture gate, FormalSpec trace contracts.
2. **P1 — consolidate existing function equivalences:** source MLP fields,
   gradient and control decisions before adding new implementations;
   audit the already supplied FormalSpec source for remaining normative gaps.
3. **P2 — one bounded mathematical research pilot:** curvature/Hessian
   diagnostic or one independently verified EQUDIF mechanism after auditing
   the available partial implementation. It initially remains **observational**, not a new default
   adaptive policy.
4. **P3 — ecosystem adapters only:** meta-control, action selection,
   relational ADTR diagnostics, conditional on avoiding duplicate APIs.

Every candidate must pass these gates:

- Ground the source version, function, inputs, outputs, restrictions and
  conceptual relation to the vMAR state.
- Decide explicitly: **reuse, formalize, adapt, aggregate, defer, discard**.
- Provide a mathematical contract and at least one known reference, one
  negative-domain test and one invariant.
- Distinguish observational diagnostics from interventions and record the
  computational cost of each.
- Use R as a reference laboratory, then implement in C23 only if the
  scientific gate warrants promotion; require R–C23 parity and strict
  regression against the frozen core.
- Document with roxygen2 and `R CMD check` on R, and API contract docs,
  CTest, and Apple Clang/C23 build on C.
- Never infer scientific superiority from agreement between languages.

## Selection record required before implementation

For each promoted mechanism, record:

- Source repository, exact revision/hash, license, function identifier.
- Mathematical assumptions, dimensions, domain and time semantics.
- Expected unique contribution and what existing vMAR feature cannot do.
- State ownership and optional configuration (no global mutable policy).
- Differential/reference baseline, tolerances, negative tests, field costs.
- FormalSpec obligation boundaries and explainability evidence.
- Explicit approval decision by the rector; only then create the new C API.

**Stop rule:** Do not launch another algorithmic experiment merely because
an available external method can be ported. Select a candidate when its
mathematical question, falsifiable contract and practical benefit are clear.

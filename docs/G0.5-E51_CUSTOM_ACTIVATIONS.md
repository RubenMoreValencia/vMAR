# G0.5-E.5.1 — Custom and parametric activation contracts

**Status:** experimental R specification and C23 implementation; independent R–C parity awaits fixture generation and execution.

## Mathematical definition

For an input row `x_i`, affine neuron `z_i = x_i * w + b`, activation `a_i = phi(z_i; alpha)`, residual `r_i = a_i - target_i`, and mean squared loss `L = sum(r_i^2)/n`, the analytical gradients are:

- `dL/dw_j = (2/n) * sum_i r_i * phi_z(z_i;alpha) * x_ij`.
- `dL/db = (2/n) * sum_i r_i * phi_z(z_i;alpha)`.
- `dL/dalpha_k = (2/n) * sum_i r_i * phi_alpha_k(z_i;alpha)` when parameters are trainable.

The fixed-parameter state is `[w_1,...,w_p,b]`; the trainable-parameter state is `[w_1,...,w_p,b,alpha_1,...,alpha_q]`. An activation is a mathematical object comprising a forward evaluation, partial derivative in the input, and (when needed) a vector of partial derivatives in its parameters. The natural learning field is `dtheta/dt = -eta * grad L(theta)`. Euler and RK4 integrate this **same** field; they do not define different activation-learning theories.

## Reference implementations and ABI

- R: `vmar_activation_spec()` constructs a validated activation; `vmar_custom_neuron_loss_gradient()` and `vmar_custom_neuron_field()` calculate its loss/gradient and field.
- C23: `include/vmar/custom_activation.h` defines a callback returning the activation value, input derivative, and parameter derivatives, with a caller-provided context. `src/vmar_custom_activation.c` implements the corresponding neuron and field. It does not allocate hidden heap memory.
- The separate C interface preserves existing built-in neuron ABI and activation IDs.
- `parameters` are fixed in the mathematical model unless `trainable = TRUE`. Trainable parameters are ordinary dynamical state coordinates, which makes their evolution observable and testable.
- R reference examples cover sine (no parameters), PReLU (slope), and Swish (beta); these examples are **research fixtures**, not a claim of optimality.

## Acceptance plan

1. R: run `devtools::document()`, `devtools::test()`, and `devtools::check()` from the R package directory.
2. With the R package loaded, set working directory to the C project and run `source("reference/generate_R_custom_activation_fixtures.R")`; it produces 40 independent references.
3. C: reconfigure and build with CMake, run CTest, then execute `vmar_test_custom_activation_parity` on `reference/vmar_custom_activation_parity.csv`.
4. Verify analytic gradients using centered finite differences, fixed/trainable dimensions, failure contracts, and both integrators.

## Research boundaries

- Adaptive activation parameters are a **hypothesis**: passing numerical parity alone does not demonstrate improved learning, stability, or generalization. Compare against fixed activation parameters at equal time and equal field-evaluation budget.
- Non-smooth functions require an explicitly documented derivative convention at kinks (for PReLU here, the derivative at zero follows the nonpositive branch). Numerical differentiation should test away from kinks.
- Custom activation fields currently integrate with generic Euler/RK4, but are **not yet connected** to the legacy augmented memory and transactional feedback-control interfaces. That adapter requires a separate state-invariant and acceptance audit.
- Callbacks must return finite values and properly sized derivative vectors; parameter ownership and lifespan remain the caller's responsibility in C.
